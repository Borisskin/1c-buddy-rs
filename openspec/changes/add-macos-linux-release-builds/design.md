## Context

См. мотивацию в `proposal.md` и договор поведения в `specs/cross-platform-release/spec.md`.

Действующий `.github/workflows/release.yml` совмещает проверку запросов на слияние, ручную сборку неизменного кандидата Windows и единственную публикацию. Windows-ветвь уже содержит ценные специальные гарантии: закреплённую версию Rust, цель MSVC, проверку PE x86-64, проверку зависимостей, контроль вложенного файла и запрет повторного использования версии. Переписывать эту ветвь целиком рискованно.

Исходный код в основном переносим: `build.rs` завершает работу без добавления ресурсов вне Windows, а Windows-специальные обращения к метаданным файла закрыты условной компиляцией. Глобальная переменная `RUSTFLAGS=-C target-feature=+crt-static` в сценарии, напротив, предназначена только для Windows и не должна наследоваться сборками Unix. Локальный `.cargo/config.toml` исключён из репозитория, поэтому чистая сборка GitHub не может полагаться на него.

Проверенные местные образцы:

- `vendor/bsl-analyzer-develop` — матрица Windows, Linux GNU и macOS ARM;
- `vendor/bsl-context-main` — независимые цели с `fail-fast: false` и отдельными архивами;
- `vendor/code-index-mcp-main` — `zip` для Windows, `tar.gz` для Unix и последующее объединение;
- `vendor/mcp-cache-ci-main` — отдельные контрольные суммы каждого архива.

## Goals / Non-Goals

**Goals:**

- добавить две цели без ослабления доказательств Windows;
- собирать каждую систему на собственной среде;
- отделить независимое изготовление кандидатов от единственной публикации;
- не допустить выпуска неполного или смешанного набора;
- сохранить одинаковый состав и понятные имена архивов;
- сделать договор сценария проверяемым обычной автоматической проверкой репозитория.

**Non-Goals:**

- подпись Apple, нотариальное заверение, подпись Windows или Sigstore;
- Linux ARM, macOS Intel, универсальный файл macOS и другие цели;
- перекрёстная сборка или контейнер выпуска;
- замена GitHub Actions другим средством;
- изменение кода MCP, его средств, настроек или сетевого поведения;
- обещание совместимости с выпусками Linux, имеющими более старую glibc, чем среда сборки.

## Decisions

### 1. Дополняющая схема заданий

Существующее задание `build-and-check` остаётся проверкой Windows. Новое матричное задание `unix-build-and-check` проверяет Linux и macOS. Аналогично, `release-candidate` продолжает создавать Windows-кандидат, а `unix-release-candidate` создаёт два кандидата Unix. `publish-release` зависит от обоих выпускных заданий.

Такой разрез сохраняет проверенный PowerShell-код Windows и не заставляет описывать несовместимые команды одной сложной матрицей. Недостаток — некоторое повторение установки Rust и кэша; оно дешевле риска скрыто изменить выпуск Windows.

### 2. Штатная сборка вместо перекрёстной

Linux собирается на закреплённом образе Ubuntu для `x86_64-unknown-linux-gnu`, macOS — на закреплённом образе Apple Silicon для `aarch64-apple-darwin`. В матрице ставится `fail-fast: false`.

Это устраняет зависимость от закрытого набора средств macOS при сборке с Linux и проверяет программу в той же системе, для которой создаётся файл. Плата — две дополнительные минуты-среды и зависимость от доступности сред GitHub.

### 3. Архив как единица передачи

Windows сохраняет `zip`; Unix использует `tar.gz`. В каждом архиве находятся ровно пять файлов без внешнего каталога. Unix-файл перед упаковкой получает право на выполнение, а проверка архива повторно вычисляет SHA-256 потока вложенного файла.

Отдельный каталог верхнего уровня был отвергнут: он изменил бы действующий договор Windows и усложнил проверку одинакового состава. Публикация одиночных исполняемых файлов также отвергнута, потому что теряются инструкции и лицензионные файлы.

### 4. Двухступенчатая неизменность

Каждое выпускное задание вычисляет SHA-256 исполняемого файла и архива и записывает целевые сведения в JSON. Задание публикации скачивает три независимых артефакта, проверяет версию, метку, редакцию, цель и обе контрольные суммы, после чего создаёт общий `SHA256SUMS.txt` для архивов.

Общий перечень строится заново, а не принимается от одной из сборок. Это исключает коллизии одинакового имени `onec-buddy-mcp` в Linux и macOS и делает публикуемые строки непосредственно проверяемыми по прикреплённым архивам.

### 5. Область `RUSTFLAGS`

Глобальная переменная `RUSTFLAGS` удаляется из сценария. Одинаковая настройка `RUSTFLAGS=-C target-feature=+crt-static` задаётся непосредственно в заданиях `build-and-check` и `release-candidate`; задания Unix её не получают.

Сохранение глобальной переменной было отвергнуто: `+crt-static` имеет иной смысл в Linux и не является допустимой политикой выпуска macOS.

### 6. Проверка договора сценария

До изменения рабочего сценария добавляется проверка `tests/release_workflow_contract.rs`. Она читает YAML как внешний договор и отдельно проверяет область `RUSTFLAGS`, цели, имена архивов, независимость матрицы и зависимость публикации от кандидатов Unix. Проверка намеренно не разбирает весь YAML и не дублирует его структуру.

Полноценный разбор YAML потребовал бы новой зависимости только для контроля файла настройки. Проверка ключевых наблюдаемых условий даёт более узкий и устойчивый рубеж.

### 7. Рассмотренные способы

Оценка пригодности относится к этому репозиторию, а не к общему качеству средств:

1. Дополняющие собственные задания и матрица штатных сред — `0,91`: сохраняет Windows-гарантии и повторяет местные образцы.
2. Три полностью отдельных сценария с общей публикацией — `0,84`: хорошо разделяет системы, но повышает риск расхождения версий и условий запуска.
3. Внедрение `cargo-dist` — `0,81`: зрелая автоматизация, но это новая крупная зависимость и более широкая переделка, чем требуется.
4. Перекрёстная сборка всех целей из Linux — `0,08`: затруднена набором средств и условиями распространения macOS.
5. Контейнер Windows/Linux плюс отдельная macOS-сборка — `0,05`: не уменьшает число сред и противоречит действующим ограничениям выпуска.
6. Ручные локальные сборки трёх сопровождающих — `0,02`: не даёт единой редакции и воспроизводимого рубежа публикации.

## Risks / Trade-offs

- Образ Linux задаёт нижнюю границу glibc → использовать явный закреплённый образ и не обещать более старые системы до отдельной проверки совместимости.
- Среда macOS Apple Silicon дороже и иногда менее доступна → независимые цели не отменяют друг друга, но общий выпуск остаётся закрыт до полного набора.
- Проверки исходного кода могут выявить скрытую зависимость от Windows → считать это ошибкой переносимости и исправлять отдельно с проверкой до расширения обещаний.
- Увеличивается объём PowerShell в публикации → использовать таблицу ожидаемых целей и единый цикл проверки вместо трёх копий логики.
- Сценарий может создать артефакты, но не доказать запуск на старых выпусках систем → не подменять сборку утверждением о полной совместимости; добавить такие среды отдельным изменением при необходимости.
- Без подписи macOS может показывать предупреждение Gatekeeper → явно документировать границу и не предлагать ослабление системной защиты как штатную установку.

## Migration Plan

1. Добавить проверку договора, которая обнаруживает отсутствие Linux и macOS в текущем сценарии.
2. Добавить матрицу проверок Unix и убедиться, что Windows использует прежнюю цель и настройки.
3. Добавить два Unix-кандидата с проверкой состава архивов и сведений о сборке.
4. Расширить единственное задание публикации проверкой и прикреплением трёх архивов.
5. Обновить краткое и подробное руководства.
6. Выполнить локальные разрешённые проверки и проверку OpenSpec.
7. Проверить запрос на слияние в трёх средах, вручную собрать и скачать кандидаты из рабочей ветви без публикации; затем выполнить ручной выпуск из `main`.

Если сборки Unix нестабильны, публикацию следует оставить закрытой и исправить соответствующую цель. Возврат к прежнему поведению выполняется отдельным изменением сценария: новые задания отключаются, а неизменённая ветвь Windows остаётся источником выпуска. Уже опубликованные материалы не перезаписываются и не удаляются.

## Open Questions

После первого успешного выпуска можно отдельно решить, нужны ли Linux musl, macOS Intel, универсальный файл macOS, подпись и нотариальное заверение. Эти решения расширяют набор целей или модель доверия и не входят в текущую реализацию.
